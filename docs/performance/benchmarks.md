# Benchmarks

Performance claims in Revenant are backed by reproducible benchmarks. This document
defines what we measure, how, and the regression policy. The suite is
[`tools/perf/`](../../tools/perf/), built in milestone M5
([story-0501](../backlog/stories/story-0501-benchmark-suite.md)).

## What we measure

| Benchmark | Driven by | Work unit |
|-----------|-----------|-----------|
| `scan-throughput` | `revenant-carve --dry-run` over an image with no filesystem | MiB scanned |
| `carve-validate` | `revenant-carve --dry-run` over a header-dense image | candidates |
| `ntfs-enumerate` | `revenant-undelete --fs-only --dry-run` over an NTFS image | entries |
| `end-to-end-hybrid` | `revenant-undelete --hybrid --dry-run` over a partitioned disk | MiB |
| `scan-simd-vs-portable` | the same fixture twice, with and without `--force-portable` | speedup × |

The fifth arrives with the SIMD path
([story-0503](../backlog/stories/story-0503-avx2-prefilter.md)); until there are two
implementations there is nothing to compare.

## How we measure

**From outside the process.** The harness starts a shipped binary and watches it. That
is what makes peak memory free (the OS reports it), instruction counting possible
(valgrind wraps the process), and real I/O visible — the fixture is a file, not an
in-memory device. It is also what a user experiences, which is the number that matters
for a tool pointed at a failing disk. Process startup is a few percent of a multi-second
run: noise, not a correction to apply.

**The suite builds nothing.** It is pointed at a build directory, or at an unpacked CI
artifact, and drives what it finds there. CMake writes `build-info.json` beside the
binaries, and the harness **refuses to report numbers from a build that was not
optimized** — a debug or sanitized binary's figures look exactly like real ones.

**Fixtures carry the work, and are not committed.** They are generated by
`revenant-imagegen` into a working directory. A case that finishes near the clock's own
noise is fixed by giving it more to do — a bigger image, more MFT records — never by
running it many times inside one timing. The fixed 32-record fixture volume is
enumerated faster than a process starts, so `ntfs-enumerate` asks for a volume with the
same files behind a larger `$MFT`.

**Every case runs `--dry-run`.** The whole engine runs and stops before writing
recovered files, because writing them measures the *destination's* disk.

**One warm-up run per case, then the timed repetitions.** The first read of a freshly
written fixture measures the page cache filling up.

**The median is the headline and the spread is the veto.** A single fast run proves
nothing on a machine with other work on it. Each case reports min, max, median and the
spread between them; on an idle machine the spread runs 1–3%.

```
python3 tools/perf/run_benchmarks.py --build-dir build/release --json out.json
```

## Baseline & regression policy

**No baseline lives in the repository.** An absolute measurement captured on one machine
means nothing on another. `tools/perf/compare_baseline.py` takes *two* result files,
which is what lets CI compare a pull request's run against `main`'s published run on the
same runner class, and what lets a developer compare two of their own.

The thresholds split by what survives being measured on a different machine:

| Metric | Threshold | Why |
|--------|:---------:|-----|
| Peak RSS | **5%** | A working set is a property of the program. |
| Instruction count | **5%** | Simulated, hence repeatable to a fraction of a percent. |
| Rate (MiB/s, candidates/s, …) | **25%** | Two runners are two machines; this catches the accidental quadratic and nothing finer. |

A rate drop past its threshold that is still inside *the baseline's own spread* is not
called a regression: a runner whose repetitions already disagreed by 35% cannot tell a
30% regression from its own noise, and a gate that cries wolf gets ignored. The spread
is a fact about the timings, so it excuses nothing on the two tight metrics.

A benchmark present in the baseline and missing from the current run **fails**: a gate
that silently stops measuring something is a fake gate. A benchmark that is new in the
current run is reported and does not fail.

**Instruction counts are comparable only against a baseline built with the same
toolchain.** `cachegrind` reports a *simulated* count, which is what makes it
repeatable — but it counts every instruction executed, libc included, so a different
compiler, libc or optimization level moves the number without anything in this
repository changing. It is gate-worthy in CI, where both runs use the same runner image,
and misleading between two developers' machines. That the gate takes two result files
rather than a committed number is what makes this safe.

Where valgrind is unavailable the count is **absent rather than faked**. That means
Windows, which valgrind has no port for; it runs on Linux, FreeBSD, Solaris/illumos and
Android. The Windows analogue would be DynamoRIO or Intel PIN, and a second
implementation is not worth it for a gate CI runs on Linux.

**The one time-based gate worth having** is a ratio measured on one machine in one
sitting — `scan-simd-vs-portable`. A ratio divides the machine out.

New optimizations must show their win here before the corresponding code merges (see
[strategy.md](strategy.md)); the SIMD path additionally must prove **bit-identical
output** via a differential test, not just speed.

## In CI

`build-release` compiles the tree once and publishes the binaries plus
`build-info.json`; `benchmarks` downloads that artifact and installs no compiler, no
vcpkg and no CMake — only valgrind. It publishes its own `benchmarks.json` and compares
it against `main`'s, when `main` has one.

The gate's verdict logic is itself tested, by `ctest` against checked-in fixtures in
`tests/fixtures/perf/` — the benchmark *numbers* are machine-dependent and untestable,
but the ruling on them is not, and it is the part that fails a merge.
